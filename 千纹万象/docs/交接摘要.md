## 1. 项目是什么

作品《千纹万象——中国传统纹样生成式数字体验》，参赛 **2026 第十四届全国大学生数字媒体科技作品及创意竞赛（CMIT）**，指定命题「民族文化 创新表达」，**报名/提交截止 2026-10-23 23:59**，赛制：校级初赛 10.24-10.28 → 赛区 11.02-11.15 → 全国总决赛 11.27-11.29。团队 ≤5 学生 + 1-2 指导教师，须报《作品介绍文档》《演示视频》《原创性声明》《AI 工具使用情况说明》（AI 使用必须如实披露）。

核心概念：**真迹 × 算法再创作**——公版真迹纹样（Owen Jones《Examples of Chinese Ornament》1867 彩色图版 + 各大博物馆公域/CC 素材）数字化入库，算法把真迹"圆窗化"后按传统构成法则重新织排，实现"千人千纹、纹纹不同"。

## 3. 运行方式

```bash
双击 千纹万象\启动作品.bat   # 自动 python -m http.server 8765 + 打开浏览器
# 或手动: cd 千纹万象 && python -m http.server 8765
```
必须走 localhost（file:// 下 canvas 被真迹图片污染无法导出）。改 js/css 后需 bump `index.html` 里所有 `?v=` 版本号（浏览器缓存旧脚本；当前值见坑 11，**bump 前先 grep 当前版本号**，见坑 12）。

   `[System.IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)` / `WriteAllText($p,$s,(New-Object Text.UTF8Encoding $false))`。

10. **`prefers-reduced-motion` 下动画的坑**（2026-10-03 已修）：入场动画的 `from` **不能含 `opacity:0`**——

  旅程总览；三级页归位（`plate → 遇见`、`album → 重塑`）；

### 四、P1-6 限时挑战（`js/challenge.js`）

60 秒按题目找出指定真迹，**答对即自动入册**（复用 `Collection.save`），
所以玩局会真的推进图鉴进度——"图鉴 → 收藏 → 成就"闭环因此多了一个入口。

- 三种题型全部**由真实数据现算**：谱系题（给定谱系）、寓意题（寓意含某词）、

> **Agnes 生图/生视频链路完全未动**，只改大语言模型（签文 + 纹博士对话）。

### 一、为什么必须加一层本地代理（本次最关键的发现）

magpie 网关（`http://127.0.0.1:3425`，本机实测 119 个模型）**不发任何 CORS 头**，
`OPTIONS /v1/chat/completions` 返回 **404**——浏览器直连必被跨域拦截。
这正是指南第 4.1 节「⚠️ Web 前端必须加后端代理」与「坑 1」写明的限制。

而本作品恰好**自带一个后端**：`_serve.py`（no-store 静态服务包装层）。
于是把它扩成一个**同源 LLM 代理**，浏览器只与本机端口通信，由它转发到上游：

```
浏览器  →  /api/llm/chat（同源，_serve.py）  →  magpie 网关 或 自定义接口
```

### 二、`_serve.py`：静态服务 + LLM 代理（含 SSRF 防护）

新增三个端点（仅同源可调，拒绝外来 `Origin`/`Referer`，避免被当成开放代理）：

| 端点 | 作用 |
|---|---|
| `GET /api/llm/status` | 探测本机 magpie 是否在运行（返回地址与版本） |
| `GET /api/llm/models` | 转发 magpie `/v1/models`（119 个模型 + 能力字段） |
| `POST /api/llm/chat` | 转发对话请求（支持 SSE 流式） |

**安全设计**：

1. **只允许 http/https**，拒绝 `file:` 等其他协议，且地址中不得内嵌账号密码。
2. **自定义接口做完整 SSRF 校验**：拒绝 loopback / 私有 / 链路本地 / 保留 / 组播 / 未指定地址——
   既查**字面主机名**，也用 `getaddrinfo` 查**解析后的每个地址**（防 DNS rebinding）；
   **重定向逐跳复验**（自定义 `HTTPRedirectHandler`），防止公网地址 302 到内网绕过校验。
   实测拒绝：`127.0.0.1` / `localhost` / `192.168.x` / `10.x` / `169.254.169.254`（云元数据）/
   `[::1]` / `0.0.0.0` / `ftp://` / `http://user:pass@host`。
3. **magpie 目标不使用用户填写的地址**：服务端自己探测固定环回地址（先读 magpie 的
   `settings.json` 端口，回落 3425），并**校验 `/api/hello` 的 `name == "magpie"`** 才认账。
   这条身份校验是「环回地址例外」成立的前提，而不是"普遍允许环回"。
4. **流式用 HTTP/1.1 分块传输**（`protocol_version = "HTTP/1.1"` + `Transfer-Encoding: chunked`）：
   否则浏览器会把整段回答缓冲完才显示，打字机效果失效。实测分片间隔 30–100ms 逐块到达。
5. 请求体上限 32MB（含 base64 图片的对话），上游读取超时 300s。

### 三、前端：双通道接入（`config.js` + `llm.js` + `index.html` + `app.js`）

面板改为「① 选择接入方式 → ② 按方式填参数」两步：

**① magpie 本机网关（默认，零配置）**
- 模型清单从 `/api/llm/models` **动态拉取**，按 provider 分组展示
  （实测：trae-cn 80 / workbuddy-ai 33 / zcode 6 = **119 个**），
  支持看图的模型标注 👁；选中即生效。
- 模型 id 不写死——用户会增删 provider（指南坑 4）。

**② 自定义 OpenAI 兼容接口**
- 三个输入框：Base URL / 模型名 / API Key，另有「测试连接」按钮
  （测试用输入框里的临时值，**失败不覆盖已有配置**）。
- 可接任何讲 OpenAI 协议的服务：官方 API、第三方中转、自建 vLLM / Ollama。

**按模型能力自动收敛参数**（新增 `LLM.clampToModel` / `supportsVision` / `supportsReasoning`）：
不同模型能力差很多（有的输出上限只有 8k），照搬 config 里的"顶格值"会被上游 400 拒绝。
拉取模型列表时把 `max_output_tokens` / `context_window` / `modalities` 记进缓存，
发请求前自动收敛输出额度（并按上下文留 20% 余量），不支持推理的模型自动摘掉 `reasoning` 参数。
无能力信息时按"支持"乐观处理，失败后走既有重试链路。

### 四、顺带修掉的两个真实缺陷

1. **签文长期静默降级**（本次才发现）：`timeoutMs` 原为 40s，那是按旧网关的直答模型定的；
   换成带深度思考的模型后，**非流式模式要等整段推理想完才返回**，实测可超过 40 秒 →
   表现为"签文总是降级成本地规则签文"（接口本身没坏，是本地提前掐断了）。
   修法：签文链路**改用流式**（每个增量都算活动）+ 上限提到 300s。
   实测修复后：`AI 签文 · group/auto-deepseek-v4-1-flash`，签文紧扣心愿与纹样。
2. **面板状态元素失联**：改造中删掉了 `#llmStatus`，而 `refreshLlmStatus()` 仍在找它 →
   状态更新静默失效。已统一到 `#llmProviderStatus`。

## 2026-10-14 · 挑战题库扩充：从 40 道题到 157 道（v20261014a）

### 起因

用户问：「这三个关卡都是固定内容吗，二次打开还是一样的吗，关卡有没有多样性？」

所以"重样"指的是**题目**重样，不是卡片重样。）

### 根因：手写词表没核对过数据

第一版 `MEANING_WORDS` 21 个词是凭印象写的，实际全库命中数：

| 锦上添花 | 1 | 安康 | 1 |

**21 个词里只有 7 个真正命中 ≥3 幅**，其余 14 个在运行时被频率校验静默

`瓷碗 / 瓷缸 / 织物 / 缂丝 / 刺绣 / 补子 / 挂毯 / 陶器 / 彩陶 / 青铜 / 漆器`

再人工剔除"有/地/成/而"这类虚词与"术博物馆"这类被切断的半截词。

**新增两个从未被用作题源的字段**：

- `name`（名称）→ **形态题**：`找出名称中含「缠枝」的真迹`——看标题即可判断
- `poetic`（签诗）→ **签诗题**：`找出签诗中含「春」的真迹`——全库 115 首无重复，
  考的是"从诗句里认纹样"

**新增第 3 关双条件题**：`找出名称含「青花」且器物考含「瓷瓶」的真迹`——
两条都写在卡片上所以有据可判，难在要同时满足；组合由数据现算（11 对合法组合），
自动跳过"一个条件蕴含另一个"的退化组合。题干里的"且"用墨金下划线标出
（`.chal-dual em`），与排除题的朱砂下划线区分开。

### 二、为什么要加媒体代理（不是多余的包装）

原实现浏览器直连 `api.agnes-ai.cn`，本次统一走代理有三个实际收益：

1. **CORS 与协议一致性**：与大语言模型通道同一套错误语义（`_proxyError` 同构的
   `_relayError`），上游错误体里的具体原因（模型不存在/额度不足）能透传到界面；
2. **SSRF 收敛到服务端一处**：前端不再需要自己维护地址白名单，
   校验逻辑与 LLM 的 custom 通道**共用同一个 `validate_upstream`**；
3. **为「任意平台」兜底**：很多第三方平台不发 CORS 头，直连必被拦——走代理后
   这些平台也能接入，这才让"用户自填平台"真正成立。

新增端点（`_serve.py`，仅同源可调）：

| 端点 | 作用 |
|---|---|
| `POST /api/media/relay` | 通用转发：`{baseUrl, key, method, path, query, body}` → 上游；响应原样回传（状态码 + 类型 + 体） |
| `POST /api/media/check` | 「测试连接」专用：**只做 SSRF 校验 + TCP 连通性探测**，不向平台发请求 |

### 三、★「测试连接」不能用真实 API 调用当探针（本次踩的坑）

第一版实现是"经代理 GET `base + '/'`，拿到任何 HTTP 状态就算可达"。实测**误判**：

| 探测方式 | 实测结果 |
|---|---|
| 经代理 `GET https://api.agnes-ai.cn/` | **23 秒**才返回（平台落地页是 Next.js 应用），15s 超时 → 报"连不上" |
| 经代理 `GET /v1/models` | **20 秒无响应**（该路径只认 POST） |
| 经代理 `GET /v1/images/generations` | 同上，挂起 |
| 直连 `https://api.agnes-ai.cn/` | 0.57 秒返回 301（差异来自代理侧对重定向链的处理） |

**结论**：平台是否"可接入"不能用它的 HTTP 响应速度衡量。改为服务端只做

实测 Agnes 地址 **8 秒内返回 `{"ok":true}`**，内网地址与不可解析域名均正确拒绝。

## 2026-10-14 · 图像 / 视频链路加固：临时故障自动重试（v20261014n）

### 一、为什么要加（缺口是实测发现的）

核查三条 AI 链路的重试现状，发现**只有 LLM 有重试，图像与视频都没有**：

| 链路 | 改前 | 位置 |
|---|---|---|
| 纹博士对话 / 签文 | ✅ 早有（`chatRetries: 2`） | `llm.js` |
| 图像生成 | ❌ 单次调用，失败即抛 | `agnes.js materialize` |
| 视频任务创建 | ❌ 单次调用，失败即抛 | `agnes.js createVideo` |

而实测中**两次视频失败都发生在"创建"这一步**：

```
视频队列已满，请稍后重试 (request id: 20261014125802977292229jG3zMr6e)
```

这是**上游容量**问题（不是请求有错），稍等重发即可。Agnes 官方错误码文档也明确
建议对 5xx 用指数退避重试（1s→2s→4s→8s）。改前撞到这类错误就直接落到
`DemoCache` 兜底——用户看到的是示例结果而不是真实生成，真实出片率白白损失。

> 注意区分：`agnes.js` 里 `waitVideo` 的 `while` 循环是**轮询**（查一个已创建任务的
> 进度），不是重试。轮询本就有超时保护，本次不动它。

### 二、实现（`config.js` + `agnes.js` + `app.js`）

**参数**（`config.js`，便于调参）：

| 参数 | 值 | 说明 |
|---|---|---|
| `mediaRetries` | 2 | 额外重试次数（总尝试 = 1+2 = 3 次） |
| `mediaRetryBaseMs` | 5000 | 退避基数，实际间隔 5s → 10s |

**判定**（`Agnes._isTransient`）——把"该不该重试"收敛到一处：

| 重试 | 不重试 |
|---|---|
| 502 / 503 / 504 / 429 / 408 | 400 / 401 / 403 / 404 / 422 |
| 网络中断（代理不可达、Failed to fetch、ECONNRESET） | 审核拒绝 |
| 业务文案：队列已满 / 繁忙 / 稍后重试 / busy / overload | 返回体为空 |
|  | 其他未知错误（保守：不重试） |

**执行**（`Agnes._withRetry`）：按 `base × 2^i` 退避，仅对可重试错误循环；
不可重试错误立即抛出，不浪费次数。

**接入点**（三处，全部只包"创建/生成"阶段）：

1. `materialize`（AI 实物渲染、AI 祈福图、视频参考图）——dataURL 无状态，重试安全
2. `createVideo`（视频任务创建）——最常撞队列的一步

**界面透出**（`app.js`，可选回调 `onRetry`）：撞到繁忙时状态行显示
「上游繁忙，正在重试（第 N 次，约 X 秒后）…」，用户不会以为卡死。
视频链路区分文案：参考图阶段「参考图生成遇到上游繁忙…」、创建阶段「视频队列繁忙…」。

> 与 LLM 重试策略**刻意不同**：LLM 那边"已开始流式输出就不重试"（怕回答重来一遍）；
> 图像/视频没有流式增量，重试不会造成可见重复，故一律按次数重试。

### 三、验收

**单元级（Node 沙箱，`_isTransient` 判定）**：17/17 通过——含队列已满、
502/503/504/429、网络中断、英文 busy，以及 401/403/400/422/404/审核/空返回
全部正确判为不可重试。

**行为级（Node 沙箱，桩掉 `_relay`）**：11/11 通过——

| 场景 | 结果 |
|---|---|
| 前两次失败第三次成功 | 调用 3 次、重试回调 2 次（退避 50→100ms）、最终成功 |
| 持续队列已满 | 尝试 3 次后抛出，错误信息保留原始原因 |
| 401 不可重试 | 只调用 1 次、无重试回调 |
| 首次成功 | 调用 1 次，不触发重试 |
| 请求体完整性 | 重试不破坏 body（`model`/`mode`/`images`/`seconds` 均正确） |
| 图像 body + b64 回传 | 正确 |

**浏览器实测（ZCode 内置浏览器，真实页面上下文）**：

| 项 | 结果 |
|---|---|
| 新代码加载 | `agnes.js?v=20261014n`、`_withRetry`/`_isTransient` 均在位 |
| 模拟队列已满（2 次后放行） | 调用 3 次、重试回调 `[{1,120ms},{2,240ms}]`、成功返回 |
| 401 场景 | 调用 1 次、无重试回调、立即抛出 |
| 视频创建（2 次后放行） | 调用 3 次、taskId 正确、body 含 reference 模式与参考图 |
| **真实链路出图** | **79 秒返回真实 COS URL，`retries: []`（重试未误触发）** |
| 八视图回归 | 零 JS 报错、零横向溢出 |
| 配置完好 | baseUrl / 两个模型名 / hasKey 全部正常 |

### 四、给后续维护

- **调参位置**：`config.js` 的 `mediaRetries` / `mediaRetryBaseMs`。视频生成单次
  等待本就长（1~3 分钟），间隔不宜再放大；若上游持续繁忙，调大 `mediaRetries` 比
  调大间隔更有效。
- **重复计费风险**：视频创建若上一次其实**已入队**（只是响应超时），重试会产生
  一次多余任务。当前 Agnes 免费档无成本风险；若日后改用付费平台，需评估是否
  改为"先查询再创建"。
- **不要给 `waitVideo` 加重试**：它是轮询，已有 `maxMs` 超时保护；再包一层重试会
  让"视频生成超时"变成"超时后又重新等 10 分钟"，用户体验更差。


## 2026-10-15 · 接入阿里云百炼：Provider 注册表 + 额度耗尽自动降级（v20261015c）

> 背景：作者在阿里云百炼账号里有一批免费额度（图像/视频合计 71 个视觉模型），
> 要求"把项目网页接进去实测"，并提出两个设计问题：
> ①「平台协议只有两个下拉，接 Seedance 等别的模型怎么办」；
> ②「额度用完了要能自动切换，不然会失败」。

### 一、为什么要重构：从"两个协议分支"到 Provider 注册表

初版把百炼实现成了 `getDialect()` 里 `if (dashscope)` 的第二个分支——能用，
但**每接一个新平台就要动一次主干判断**，与 Lily/Cherry Studio 这类成熟客户端
的做法背道而驰。本次对照调研了主流智能体的接入设计：

| 产品 | 做法 | 对我们最有价值的一点 |
|---|---|---|
| Cherry Studio | 内置 60+ 服务商模板，7 类协议（OpenAI/Anthropic/Gemini/Bedrock/Azure/本地/特殊网关）；自定义服务商只需"API Key + API 地址（可选）"，模型列表从端点拉取 | **协议类型是模板属性，不是硬编码分支** |
| LobeChat | Provider 注册表 + 每家的 `createProvider` 声明请求形状；自定义端点也是注册表里的普通成员 | 加平台 = 加一个声明，不改主干 |
| 通用规律 | 「平台身份」（地址/Key/模型名）与「协议形状」（怎么发请求）分离 | 面板字段固定四项，形状由注册表决定 |

据此重构为：`config.js` 里一张 **`MEDIA_PROVIDERS` 注册表**（id / 名称 / 默认地址 /
默认两个模型名），`agnes.js` 按 provider id 分派 `_dispatchImage` / `_dispatchVideoCreate`。
接入新平台的确切步骤（写给后续维护）：

1. `config.js` 的 `MEDIA_PROVIDERS` 加一项（含默认 baseUrl 与两个模型名）；
2. `agnes.js` 的 `_dispatchImage` / `_dispatchVideoCreate` / `waitVideo` 各加一个 `case`；
3. 若该平台请求形状需要服务端配合（如需加特殊头、需拆分同步/异步两步），在
   `_serve.py` 的 `_media_post` 里按 `provider` 加分支（百炼先例：`/.dashscope-image`
   / `/.dashscope-video` / `/.dashscope-task` 三个虚拟端点）；
4. 面板下拉会自动出现该项（选项在 `index.html` 手工同步一次，共两行）。

### 二、额度耗尽自动降级（quota fallback）

百炼免费额度**按模型计、用完即停**：额度用尽返回 `403 AllocationQuota.FreeTierOnly`，
且这个 403 与"Key 无效"的 403 长得一样——如果按普通不可重试错误处理，用户看到的是
一句没有下文的报错。本次实现：

- `_isQuotaExhausted(e)`：按 403 + 业务文案（`FreeTierOnly` / 额度 / Arrearage）识别；
- 图像与视频各配一条**备用链**（面板可编辑，逗号分隔，存 localStorage）：
  主模型额度耗尽 → 自动沿链降级，直到链上全部耗尽才真正报错；
- 降级过程在界面上透出（「「A」额度已耗尽，自动切换备用模型「B」…」），
  结果标签显示**实际出图的模型**（不是配置里的主模型）——避免"以为还在烧 A"的假披露。

默认链（依据 2026-10-15 实测额度）：
`qwen-image-2.1-pro`(剩 9) → `qwen-image-2.0`(剩 100) → `qwen-image-2.1-turbo`(剩 10)；
`wan2.7-i2v`(剩 40) → `wan2.6-i2v`(剩 50) → `wanx2.1-i2v-turbo`(剩 200)。

### 三、百炼接入的三个实测坑（都已写进代码注释）

1. **图像是同步接口、且只收 dataURI**：`POST {base}/api/v1/services/aigc/multimodal-generation/generation`，
   参考图放 `input.messages[].content[].image`，必须是 `data:image/png;base64,..` 形式；
   裸 base64 串会被拒（`DashScope rejected the request`）。
2. **视频是异步接口，参考图字段两代不通用**：
   - `wan2.7+` / `wan3.0`：`input.media = [{url, type:"first_frame"}]`（对象数组）；
   - `wan2.6` 及更早（`wan2.6/wan2.5/wanx2.1/wan2.2`）：`input.img_url`（字符串）。
   写错形状不会立刻报错——任务**先受理成功**（返回 task_id），跑十几秒后才
   `FAILED: Field required: input.img_url`。所以备用链可跨代混填，
   由 `_dashscopeCreateVideo` 按模型名前缀自动分派形状。
   创建必须带 `X-DashScope-Async: enable` 头，出片结果在轮询响应的 `output.video_url`。
3. **百炼的 OpenAI 兼容入口没有图像生成**：`/compatible-mode/v1/images/generations`
   返回 404，只有 chat 等文本类接口——所以百炼的图像/视频必须走原生形状，
   不能像 Agnes 那样填 OpenAI 协议路径。

## 2026-10-15 · 面板内接入任意平台：自定义平台（通用协议模板，v20261015f）

### 一、能力

「模型接入设置」面板的「平台（协议）」新增第三项 **自定义平台（通用协议模板）**。
选中后出现「协议详情」区：选一个**协议模板**自动填好请求路径与请求体，剩下填
平台地址、两个模型名、Key 即可使用——**不写代码、不开编辑器就能接入新平台**。
请求仍经同源代理转发（SSRF 校验照旧），认证头与额外请求头由服务端按白名单校验后附加。

### 二、协议描述（localStorage 键 `qianwen_media_custom_proto`）

| 分区 | 字段 |
|---|---|
| 图像（同步） | 请求路径 / 请求体模板 / 结果字段名 / 额外请求头 |
| 视频（创建+轮询） | 创建路径 / 创建请求体模板 / 任务号字段名 / 轮询路径 / 轮询地址 / 轮询间隔 / 状态字段名 / 成功词 / 失败词 / 进度字段名 / 结果字段名 / 额外请求头 |
| 认证 | 认证头名 / 认证前缀 |

- **模板占位符**：`{model} {prompt} {image} {seconds} {taskId}`；
  恰为占位符 → 整体替换，嵌在串里 → 插值；**一律替换为字符串**。
  轮询路径另支持 `{taskId}` 与 `{model}` 插值。
- **取值一律用「字段名」而非路径**（`_find` 递归查找），留空 = 自动：
  图像结果 url → b64_json → image；任务号 task_id → video_id → id；
  状态 status → task_status；结果 video_url → url。
- **服务端头规则**（`_serve.py`，只对 `provider=custom` 生效）：头名须匹配
  `[A-Za-z][A-Za-z0-9-]{0,63}` 且不在黑名单（Host / Content-Length / Connection /
  Transfer-Encoding / Content-Type / Cookie 等），头值无控制字符、≤512，最多 8 个。

### 三、实测量出来的四条硬规矩（都写进了代码注释）

1. **`X-DashScope-Async: enable` 只能挂"视频创建"，不能挂图像、也不能挂轮询**——
   挂图像或轮询 GET 都会被百炼 403（`does not support asynchronous calls`）。
   因此额外请求头按接口分组（图像/视频各自一组），且轮询只带认证头。
2. **`{seconds}` 一律替换为字符串**：Agnes 收到数字型 seconds 直接
   400 `invalid_json`；百炼两种都收（已实测）。要数字的字段在模板里写死字面量。
3. **TUN + fake-ip 代理环境下 SSRF 守卫必须放行 198.18.0.0/15**：这类代理
   （Clash/Mihomo 默认 fake-ip 池）把**所有**域名解析到 198.18.x.x，不放行则
   等于"拒绝一切"；该段是 RFC 2544 基准段、无真实服务。环回/RFC1918/链路本地
   等原样拦截（已实测：127.0.0.1 / 192.168.x / 10.x / 169.254.x 仍被拒）。
4. **`I18n.tpl(zh, en, ...)` 中文侧不做参数替换**——中文提示要调用方自己拼好，
   否则界面会原样显示 `{0}`（本次踩过，已在 readProtoForm 注释里标注）。

### 四、预置模板（只收已实测形状；新增预置 = 给 `config.js` 的
`CUSTOM_PROTO_PRESETS` 加一条"默认值 + 覆盖"的数据）

## 2026-10-15 · 启动器实测：两个真问题已修（v20261015g）

用户反馈"启动脚本有点问题"，实测复现并修掉两处——**脚本机制本身没错，错在
两处会让"看起来正常、实际不能用"的静默状态**：

### 问题一：旧 Key 静默顶掉预填 → 页面显示"已接入"，一用就 401

复现：浏览器里存着一个旧 Key（51 位、非百炼格式、对百炼返回 401 已失效），启动器投放的
`media.key` 因"非空不覆盖"被跳过 → 页面仍显示"✓ 已接入 · 阿里云百炼"，
实测 API 探测返回 **401 Invalid API-key**。因 Key 输入框从不回显，用户看不到、
无从排查。

修复（`js/app.js`）：**媒体 Key 改为每次载入都以 `_local/keys.local.js` 为准**
（不一致就覆盖）；平台/地址/模型/备用链/协议仍是"空则填、非空不覆盖"，
面板里可见的手改不受影响。（开发机上换 Key 请直接改 `_dev\keys.local.js`。）
实测：把旧 Key 塞回 localStorage → 刷新页面 → 自动校正为百炼 Key，探测恢复正常。

### 问题二：关窗后服务残留 → 再次启动出现"两个服务同端口"且不提示

复现：强杀启动器的 cmd（等价于某些关窗路径）后 python 服务进程仍在监听 8765；
再次启动时 Windows 的 SO_REUSEADDR 允许第二个进程绑定同一端口 → 出现
**两个服务同时监听 8765** 的怪状态（页面时好时坏），且启动器毫无提示。

修复（`serve.ps1` 新增 `Clear-StaleListener`，启动前执行）：
- 按**进程命令行**识别并清理本作品残留的服务（`python … _serve.py 8765` /
  `-m http.server 8765`）——实测双监听时 `Get-NetTCPConnection` 只报其中一个，
  不能依赖端口枚举；
- 端口被**别的程序**占用则明确报错退出，绝不误杀。
实测：故意留两个残留服务 → 启动器输出两条"[i] 清理上次残留的服务进程（PID …）"
并干净启动，端口只剩一个新服务。

### 附：已知的无害残留

- 强制关窗（X / 任务管理器）不会执行启动器的收尾清理，`_local\keys.local.js`
  会留在项目里——下次启动会覆盖刷新它，`.gitignore` 与 `打包提交.bat` 也都排除
  该目录，不会进提交包；介意的话手动删掉 `_local` 即可。
- 正常关闭（Ctrl+C 或让服务窗口自行结束）会走完整清理路径（实测通过）。


## 2026-10-15 · 事故复盘：页面"所有点击都没反应"（v20261015h）

**现象**：用户报告"页面点击没有用"。实测复现：点击导航后 hash 变了（`#jian`/`#fang`…），
但可见视图永远停在 home，且控制台无报错。

**根因**（自定义平台功能引入，属于本次开发的回归）：
1. `_protoMerge` 首版只判了 `over === undefined`、**漏判 `null`**；
2. 从没存过协议配置的浏览器里 `JSON.parse(...||"null")` 得到 `null`，合并结果变成 `null`；
3. `fillProtoForm(null)` 里 `proto.image.path` 抛 TypeError；
4. `fillMediaForm` 跑在 `buildLlmSetup()` 里 → `buildLlmSetup` 中断 →
   `DOMContentLoaded` 回调**从中间断开**，连文件末尾的
   `window.addEventListener("hashchange", routeFromHash)` 都没执行 →
   **路由失效 = 所有点击看起来都没反应**（页面本身渲染正常，所以极具迷惑性）。

之前没测出来的原因：我的测试浏览器里都存过协议配置（自定义平台联调留下的），
所以走不到 null 分支。

**修复**（三处）：
- `agnes.js` 的 `_protoMerge`：`over` 为 `null` 或 `undefined` 都回落到 `base`；
- `app.js` 的 `fillProtoForm`：入口先做 `_protoMerge(CUSTOM_PROTO_DEFAULTS, proto)`
  归一化兜底，面板回显绝不因空值抛错；
- `app.js` 初始化加固（防同类事故再发生）：
  ① `hashchange` 路由与返回按钮绑定**提到初始化最前**；
  ② 各模块初始化包进 `safeInit(name, fn)`，单个模块抛错只报控制台、不影响其余

### 二、★修掉一个真实缺陷：签文额度被推理吃光（阻塞演示）

**现象**：同一份签文请求，DeepSeek 官方 API **稳定失败**并报
"模型这次把额度用在了推理上，没能给出回答"。

**根因**（实测三组对照）：

| 组合 | 结果 |
|---|---|
| `max_tokens=800` + reasoning 默认（开） | ✗ 推理烧完 800，正文 0 字，`finish_reason=length` |
| `max_tokens=800` + `reasoning:false` | ✗ 同样失败——**DeepSeek 官方 API 默认就思考**，该开关对它无效 |
| `max_tokens=8192` + reasoning 默认 | ✓ 正文 112 字，推理约用 420~800 |

即：签文额度 `800` 是按"直答模型"定的，而 DeepSeek 官方 `deepseek-flash`
默认 `effort=high`，**推理与正文共享同一份 max_tokens**。附带实测：
`reasoning_effort:low` 无效；`reasoning:{"effort":"low"}` 与
`thinking:{"type":"disabled"}` 有效——但后者是 DeepSeek 私有形状，
作品要保持通用接入，不采用。

**修法**（保持通用，不硬编码任何厂商私有参数）：
1. `config.js` 新增 `qianMaxTokens: 4096`（上限而非预扣，对不推理的模型无代价）；
2. `llm.js::makeQian` 首次失败且错误含"推理"时，**显式关掉 reasoning 再试一次**
   ——认这个参数的平台就能在同一份额度里正常落正文，不认的会忽略它。

### 三、★修掉第二个真实缺陷：模板引擎缺"数字占位符"（阻塞视频）

**现象**：自定义平台创建视频任务**先受理成功**（返回 task_id），几秒后
`FAILED: InvalidParameter: Input should be a valid integer: parameters.duration`。

**根因**：`_fillTpl` 把 `{seconds}` 一律替换成**字符串**（2026-10-15 为 Agnes
定的规矩，因为 Agnes 只认字符串），而百炼 `parameters.duration` 必须是**整数**。
这种"先成功后失败"最难排查——任务号都拿到了，错误却在轮询阶段才浮出。

**修法**：模板语法新增数字占位符 **`{seconds:num}`**（`:number` / `:int` 同义）：
字符串恰为 `{token:num}` 时替换为**数字**，非数字抛可读错误；
嵌在串里的插值形态不参与转换（把数字塞进字符串里没有意义）。
百炼预置模板已改用 `{seconds:num}`。实测：`duration` 得到 `number 5`；
Agnes 同形与通用模板的 `seconds` **仍是字符串**（无回归）。

### 四、★修掉第三个真实缺陷：跨代备用链形状不通用（阻塞额度降级）

**现象**：主模型 `wan2.7-i2v` 额度耗尽 → 自动降级到 `wan2.6-i2v` → 立刻 FAILED。

**根因**（实测对照）：

| 模型 + 形状 | 结果 |
|---|---|
| `wan2.7-i2v` + `input.media[]` | 403 `AllocationQuota.FreeTierOnly`（额度耗尽，属预期） |
| `wan2.6-i2v` + `input.media[]` | ✗ FAILED `Field required: input.img_url` |
| `wan2.6-i2v` + `input.img_url` 字符串 | ✓ SUCCEEDED |

即：**wan2.7+ 收 `media` 对象数组，wan2.6 及更早只收 `img_url` 字符串**，
而协议模板只能描述一种形状 → 备用链跨代混填时必然失败。
（原生 `dashscope` 分支早有 `_dashscopeCreateVideo` 按代分派，**自定义模板缺这一层**。）

**修法**：模板新增**备用请求体**（面板可编辑，属纯数据）：
- `video.altMatch`：模型名片段（逗号分隔、不区分大小写），命中则改用备用体；
- `video.altCreateBody`：备用请求体模板（留空 = 不使用，默认行为完全不变）。
百炼预置已配 `wan2.6,wan2.5,wan2.2,wanx` → `img_url` 体。

**实测**（真实 UI 点「AI 全视角视频」）：
`wan2.7-i2v` 额度耗尽 → 界面提示"自动切换备用模型「wan2.6-i2v」" →
任务受理成功 → 出片，`readyState=4`（可播放），标签正确显示**实际模型
`wan2.6-i2v`**（不是配置里的主模型，无假披露）。

### 六、排障记录：一个**非项目问题**（避免下次误判）

实测初期百炼两个域名报
`SSL: UNEXPECTED_EOF_WHILE_READING`（TLS 秒断），一度疑似代码问题。逐层定位：

| 检查 | 结果 |
|---|---|
| 经代理 TCP 连通性 | ✓ 通（8s 内 `{"ok":true}`） |
| DNS 解析 | 全部域名解析到 **198.18.x.x**（Clash/Mihomo fake-ip 池） |
| 原始 TLS 握手（逐域名） | 百炼两域名 FAIL，`api.deepseek.com` **OK** |
| **真实 IP 直连 + SNI** | ✓ **TLS OK 且 HTTP 200**（`x-dashscope-workspace` 正确） |
| 稍后重测 | 全部域名恢复正常，出图成功 |

**结论**：本机在跑 `iKuuuVPNCore`（TUN + fake-ip），它对阿里云域名的转发**偶发故障**，
与作品代码无关。**给后续维护**：遇到 `UNEXPECTED_EOF_WHILE_READING` 且仅某几家
域名失败时，先按上表逐层定位（DNS 是否 fake-ip → 原始 TLS → 真实 IP 直连），
不要改代码。另注：本机 curl 走 schannel 后端，对这类问题**误报率高**，
排查请用 Python urllib（与 `_serve.py` 同一套栈）。

### 二、★修掉第四个真实缺陷：端点不报能力字段 → 顶格 max_tokens 必然 400

**现象**：页面「测试连接」通过（那条只发 `max_tokens:16`），但**纹博士与签文一用就失败**：

```
This model's maximum context length is 262144 tokens. However, you requested
262144 output tokens and your prompt contains 343 characters (more than 0
characters, which is the upper bound for 0 input tokens).
```

**根因链**：项目 `chatMaxTokens: 262144` 是"上限的上限"，靠 `LLM.clampToModel()`
用 `/v1/models` 报的 `context_window` / `max_output_tokens` 自动收敛。
**该端点不返回这两个字段** → `clampToModel` 无数据可收敛（`rememberCaps` 里
`ctx>0` 判断失败，缓存成 0）→ 原样发 262144 → 而该模型上下文是**输入+输出共享**，
顶格输出必然越界 → 400。

**修法**（`llm.js`，通用自愈，不针对任何厂商）：

1. 新增 `LLM._learnContextLimit(msg)`：从上游 400 文案里正则提取真实上限
   （`maximum context length is N` / `context length is N` / `context window N`），
   写进能力缓存；
2. `_chatOnce` 拆出 `_chatOnceInner(…, learned)`，命中"上下文超限 + 学到新值"时
   **重发一次**；`learned` 计数保证最多一层，不会死循环；
3. 只认"上下文超限"这一类错误，其它 400（参数名错 / 模型不存在）行为不变。

**实测**：首次 400 → 学到 `context=262144` → 自动重发 → **2.7 秒流式回答（6 分片）**；
缓存显示 `{"qwen3.8-27b":{"context":262144,…}}`。

> **给后续维护**：这是"端点不报能力字段"的通用兜底。若接入的平台连上限都不写进
> 错误文案，仍会失败——那时才需要用户在 `config.js` 里手动调低 `chatMaxTokens`。

### 四、排障记录：两次"按钮点不动"是工具层现象，非页面缺陷

Playwright 对 `#llmCustomTest` / `#llmCustomSave` 报
`pointer probe returned no click point`，但 CDP 复核显示：元素存在、未 disabled、
在视口内（rect 完全可见）、且 `elementFromPoint(中心)` **就是该按钮本身**（无遮挡）。

再用坐标点击绕过即可。
